## 1. 启动与初始访问

```bash
docker compose up -d
```

查看容器状态：

```bash
docker ps
```

获取初始 root 密码：

```bash
docker exec -it gitlab grep 'Password:' /etc/gitlab/initial_root_password
```
这个文件不存在，通常是因为 GitLab 的初始密码文件在生成后**超过 24 小时**会被自动删除，或者你的容器尚未完全初始化成功。不过别担心，我们可以通过 GitLab 的 Rails 控制台直接重置 root 密码，这是最稳妥的方式。

### 🔑 通过 Rails 控制台重置 root 密码

请在你的宿主机终端中，按顺序执行以下命令：

**1. 进入 GitLab 容器的 Rails 控制台**
```bash
docker exec -it gitlab gitlab-rails console -e production
```

执行后你会看到一个 `irb(main):001:0>` 的提示符，表示已成功进入控制台。

**2. 在控制台中查找 root 用户并重置密码**
依次输入以下 Ruby 命令（每输入一行按一次回车）：
```ruby
# 查找 root 用户
user = User.find_by(username: 'root')

# 设置新密码（请替换 'YourNewPassword123' 为你想要的密码）
user.password = 'YourNewPassword123'
user.password_confirmation = 'YourNewPassword123'

# 保存更改
user.save!
```

当 `user.save!` 返回 `true` 时，表示密码修改成功。

**3. 退出控制台**
```ruby
exit
```


完成以上步骤后，你就可以使用 `root` 用户名和刚刚设置的新密码登录 GitLab 了。

### 💡 补充说明

*   **密码复杂度**：GitLab 默认要求密码至少 8 位，并包含大小写字母和数字，设置过于简单的密码可能会被拒绝。
*   **容器状态**：请确保 GitLab 容器处于正常运行状态（`Up`），如果容器刚启动，请等待其完全初始化（通常需要 2-5 分钟）后再执行上述操作。
*   **备选命令**：除了进入控制台，也可以尝试直接使用 `gitlab-rake "gitlab:password:reset[root]"` 命令来重置 root 密码。
*   **数据持久化**：如果你的 `docker-compose.yml` 没有正确挂载 `/etc/gitlab` 目录，容器重启后配置和密码文件可能会丢失。请确保你已经按照之前的配置完成了持久化卷的挂载。

```text
http://服务器IP
```

或配置 HTTPS 后访问：


首次登录后应立即修改 root 密码。

## 2. HTTPS 配置（或参考7以后内容）

将 `external_url` 改为 HTTPS 地址：

```ruby
external_url 'https://gitlab.example.com'
```

将证书文件放入挂载目录，例如：

```text
config/ssl/gitlab.example.com.crt
config/ssl/gitlab.example.com.key
```

在 `gitlab.rb` 中指定证书路径：

```ruby
nginx['ssl_certificate'] = "/etc/gitlab/ssl/gitlab.example.com.crt"
nginx['ssl_certificate_key'] = "/etc/gitlab/ssl/gitlab.example.com.key"
```

修改后执行：

```bash
docker exec -it gitlab gitlab-ctl reconfigure
```

若使用 Let's Encrypt：

```ruby
letsencrypt['enable'] = true
```

前提是域名已解析，且 80 端口可从外网访问。

## 3. 项目创建与代码推送

建议按团队建立 Group，项目统一设为 Private。

在GitLab中创建项目和推送代码
装好GitLab以后，很多人的第一直觉是直接建一个项目然后把本地代码推上去。这条路径基本走通，但提前了解几个概念会让你少走弯路：

- Group（群组） ：相当于团队或部门，下面可以建多个Project。我建议你先在GitLab里按团队结构建几个Group，比如 backend 、 frontend 、 infra ，而不是让每个工程师各自建个人项目
- Project（项目） ：对应一个代码仓库，可以设置可见性（私有、内部、公开）
- Visibility ：公司内部的GitLab，建议统一设成Private，避免代码被搜索引擎收录
创建项目的入口在页面左上角“新建项目”。创建好之后，页面上会直接给出下面几个URL：

- HTTP地址： http://gitlab.example.com/group/project.git
- SSH地址： git@gitlab.example.com:2222/group/project.git
如果你是本地已经有一个Git仓库，直接照着页面提示操作：

```shell
cd existing_project
git remote add origin git@gitlab.example.com:2222/group/project.git
git push -u origin main

```

如果你是本地还没有仓库，且没有本地项目 那就：

```shell
git clone git@gitlab.example.com:2222/group/project.git
cd project
# ...干活、提交、推送


```


本地创建项目后推送代码：

```bash

git commit -m "init"
```

## 4. 项目导入与迁移

从旧 GitLab 迁移时，可使用完整备份恢复：

```bash
gitlab-backup restore BACKUP=备份文件名
```

恢复前通常需要停止写入服务：

```bash
gitlab-ctl stop unicorn
gitlab-ctl stop sidekiq
gitlab-backup restore BACKUP=xxx
gitlab-ctl reconfigure
gitlab-ctl start
```

注意：恢复对象是完整实例备份，不是单个项目导出。

## 7. 注意事项

- 修改 `/etc/gitlab/gitlab.rb` 后必须执行 `gitlab-ctl reconfigure`。
- 部署前确认 80/443/22 端口未被占用。
- 防火墙和安全组需放行对应端口。
- 邮件通知需额外配置 SMTP，否则注册确认、密码重置等功能可能不可用。
- 备份保留时间只是清理策略，仍需定期验证备份可恢复。
- 生产环境建议固定 GitLab 镜像版本，避免 `latest` 带来的升级不确定性。

以下是一套在同一个 Docker Compose 中同时管理 Nginx 和 GitLab、由 Nginx 容器统一终止 HTTPS 的完整配置。核心原则是：**GitLab 容器只作为 HTTP 后端运行，不暴露任何端口到宿主机公网；所有 80/443 流量由 Nginx 容器接收、解密并反向代理到 GitLab 服务名**。

---

## 架构与网络模式选择

推荐让 Nginx 和 GitLab 处于**同一个自定义 Docker 网络**中。这样 Nginx 的 `proxy_pass` 可以直接写 **GitLab 的服务名**（如 `http://gitlab:80`），无需经过宿主机端口映射，GitLab 容器也**完全不需要** `ports` 暴露到宿主机，从网络层面隔离了公网直接访问 GitLab 的可能。

```text
公网 → 宿主机 80/443 → Nginx 容器（SSL 终止）
                           ↓ 自定义 Docker 网络（服务名解析）
                       GitLab 容器 :80
```

如果沿用“GitLab 端口映射到 127.0.0.1:8929、Nginx 用宿主机网络访问”的方式，也可以工作，但会多一层 NAT，并且 GitLab 端口仍需绑定本地，安全性依赖绑定地址的约束。同一自定义网络是更干净、更符合 Compose 编排的方式。

## Docker Compose 完整配置

```yaml
services:
  gitlab:
    image: gitlab/gitlab-ce:latest
    container_name: gitlab
    restart: always
    hostname: 'gitlab.example.com'
    # 注意：没有 ports，容器不向宿主机暴露任何端口
    environment:
      GITLAB_OMNIBUS_CONFIG: |
        # 最终用户访问的 HTTPS 地址，必须与 Nginx server_name 完全一致
        external_url 'https://gitlab.example.com'

        # 1. 禁用内置 HTTPS，让 GitLab 只监听 HTTP
        nginx['listen_https'] = false
        nginx['listen_port'] = 80
        letsencrypt['enable'] = false

        # 2. 信任来自 Nginx 容器的代理（使用自定义网络的子网）
        gitlab_rails['trusted_proxies'] = ['172.20.0.0/16']

        # 3. 强制 GitLab 识别外部请求为 HTTPS
        nginx['proxy_set_headers'] = {
          "X-Forwarded-Proto" => "https",
          "X-Forwarded-Ssl" => "on"
        }
    volumes:
      - './gitlab/config:/etc/gitlab'
      - './gitlab/logs:/var/log/gitlab'
      - './gitlab/data:/var/opt/gitlab'
    shm_size: '256m'
    networks:
      - gitlab-net

  nginx:
    image: nginx:stable
    container_name: gitlab-nginx
    restart: always
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - './nginx/conf.d:/etc/nginx/conf.d:ro'
      - './nginx/ssl:/etc/nginx/ssl:ro'
    depends_on:
      - gitlab
    networks:
      - gitlab-net

networks:
  gitlab-net:
    driver: bridge
    ipam:
      config:
        - subnet: 172.20.0.0/16
```

**GitLab 侧关键配置解读**：

- **`nginx['listen_https'] = false`** 和 **`letsencrypt['enable'] = false`**：彻底关闭 GitLab 内置的 SSL 能力，避免与外部 Nginx 形成双重 SSL 或证书冲突。
- **`trusted_proxies`**：必须与自定义网络的子网一致（示例中为 `172.20.0.0/16`）。如果不配置或配置错误，GitLab 会将所有请求的来源 IP 识别为 Nginx 容器的 IP，可能导致安全校验异常和 422 错误。
- **`proxy_set_headers`**：显式声明 `X-Forwarded-Proto: https` 和 `X-Forwarded-Ssl: on`。这是避免登录、修改设置等 POST 请求返回 **422 “Can't verify CSRF token authenticity”** 的关键配置。

## Nginx 容器配置

将以下文件放在 `./nginx/conf.d/gitlab.conf`，证书放在 `./nginx/ssl/` 下。

```nginx
# HTTP 强制跳转 HTTPS
server {
    listen 80;
    server_name gitlab.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name gitlab.example.com;

    ssl_certificate     /etc/nginx/ssl/gitlab.example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/gitlab.example.com.key;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256;

    # GitLab 默认允许的请求体较大，上传代码包、制品时需要
    client_max_body_size 1024m;

    location / {
        # 直接使用 Docker Compose 中的服务名，无需端口映射
        proxy_pass http://gitlab:80;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 大文件上传和长时间操作需要的超时设置
        proxy_read_timeout 3600;
        proxy_request_buffering off;
    }
}
```

**Nginx 侧要点**：

- `proxy_pass http://gitlab:80` 中的 **`gitlab` 就是 Compose 中的服务名**，Docker 内置 DNS 会将其解析到 GitLab 容器的 IP，无需关心容器 IP 变化。
- `X-Forwarded-Proto $scheme` 是 Nginx 传递给 GitLab 的 **HTTPS 信号**，与 GitLab 侧的 `proxy_set_headers` 形成双重保障。缺少这个头，GitLab 会认为请求是 HTTP 的，引发重定向循环或 CSRF 失败。
- `client_max_body_size` 和 `proxy_request_buffering off` 对大文件上传和 Git LFS 操作尤为重要，避免默认 1MB 限制导致推送或上传失败。

## 需要注意的细节

**1. 启动顺序与重试**
`depends_on` 只保证容器启动顺序，不保证 GitLab 内部服务就绪。GitLab 首次启动期间，Nginx 可能短暂返回 502。这是正常现象，等待 GitLab 就绪后即可恢复。如果希望 Nginx 不提前接受流量，可以给 GitLab 配合健康检查，但这会增加配置复杂度，对于单机部署通常不必强制。

**2. SSH 克隆端口**
上述配置只处理了 HTTP/HTTPS。如果还需要通过 SSH 克隆代码，需要单独暴露 SSH 端口并告知 GitLab：

```yaml
# 在 gitlab 服务的 environment 中加入
gitlab_rails['gitlab_shell_ssh_port'] = 2222
```

同时在 Compose 中为 GitLab 增加 `ports: - "2222:22"`。否则 GitLab 界面显示的 SSH 克隆地址会缺少端口号，导致 `git clone` 连接失败。

**3. `external_url` 协议必须与实际访问一致**
`external_url` 必须严格写成 `https://域名`。如果写成 `http://`，GitLab 生成的重定向和链接会出现协议不匹配，触发 422 或登录态异常。

**4. 如果改用 `127.0.0.1` 端口映射模式**
若你出于特定原因不用自定义网络，而是让 Nginx 通过宿主机 `127.0.0.1:8929` 访问 GitLab，则需要把 GitLab 的 `ports` 设为 `"127.0.0.1:8929:80"`，Nginx 的 `proxy_pass` 改为 `http://127.0.0.1:8929`，`trusted_proxies` 应加入 `127.0.0.1`。两种模式的核心 GitLab 环境变量（`listen_https = false`、`proxy_set_headers`）完全一致，区别只在于 Nginx 到 GitLab 的寻址方式。
